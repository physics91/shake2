# 비밀방 암호의 남은 위험 해결

## Goal

비밀방 작업(`278c698`)의 남은 위험 두 가지를 없앤다.

1. `ws://`에서는 방 암호가 평문으로 간다.
2. 틀린 암호의 0.5초 지연이 접속 하나에만 걸려, 접속을 여러 개 열거나 다시 접속하면 추측을 그만큼 빨리 할 수 있다.

## Scope

- 서버: `server.ts`(TLS, 접속 주소), `main.ts`(환경 변수), `lobby.ts`(주소별 암호 확인 간격), `room.ts`의 `Peer`(주소).
- 개발·미리보기 프록시: `vite.config.ts`의 `/ws` 프록시가 `X-Forwarded-For`를 붙이게(`xfwd`).
- 문서: README 서버 환경 변수와 비밀방 문단, FIDELITY §14 "비밀방(복원판 서버)" 줄.
- 범위 밖: 화면 낭독기의 암호 칸 읽기(한글 입력을 위한 text 칸 유지), 여러 주소에서 나눠 하는 추측(분산 공격), 주소당 접속 수 제한 같은 일반 DoS(줄은 접속마다 하나라 접속 수만큼 커짐).

## Approach

### 1. TLS (`wss://`)

- `TLS_CERT`·`TLS_KEY`(PEM 파일 경로)가 둘 다 있으면 서버가 `node:https`로 듣고 `wss://…/ws`로 안내한다. 하나만 있으면 시작하지 않는다. 새 의존성 없음.
- TLS 없이 루프백이 아닌 주소(`HOST=0.0.0.0` 등)로 들으면 시작 로그에 경고 한 줄(암호가 평문으로 감).
- 클라이언트는 이미 https 페이지에서 `wss://`를 쓰고, 서버 주소 칸에 `wss://`를 넣을 수 있어 바꿀 것 없음.
- 기본값은 지금처럼 평문(LAN 대전 호환, 원본도 평문 TCP). 인터넷에 열 때 TLS를 켜도록 README에 적는다.

### 2. 주소별 암호 확인 간격

- 서버가 접속마다 주소 키를 정한다: IPv4는 주소 그대로, IPv4-mapped IPv6는 IPv4로, IPv6는 앞 64비트(/64)로 묶는다(주소를 바꿔 가며 우회하지 못하게).
- `X-Forwarded-For`는 소켓 주소가 믿는 프록시일 때만 읽는다. 믿는 프록시는 루프백(같은 기계의 vite·미리보기 프록시)과 `TRUST_PROXY`(쉼표로 나눈 주소)다. 오른쪽부터 믿는 프록시를 건너뛰고 처음 나오는 주소를 쓴다. 아무 접속이나 보낸 헤더는 무시해 위조로 새 키를 얻지 못한다.
- 문서의 설정(같은 기계의 vite·미리보기 프록시 뒤)에서 모든 브라우저가 127.0.0.1로 묶이지 않도록 `/ws` 프록시에 `xfwd: true`를 준다. 실제로 헤더가 오는지 Chromium 확인에서 본다.
- 로비는 주소 키마다 암호 확인을 한 번에 하나씩, 간격을 두고 한다.
  - 빈 암호는 확인하지 않고 바로 `join-password`(지금처럼).
  - 암호가 있으면 그 주소의 줄에 넣고, 확인할 때가 되면 확인한다. 맞으면 입장, 틀리면 바로 `join-password`를 보내고 다음 확인을 늦춘다.
  - 늦추는 시간: 연속 n번째 틀림 뒤 min(500 ms · 2^(n−1), 30 s). 10분 동안 틀림이 없으면 잊는다. 맞춰도 줄이지 않는다(제 비밀방으로 세는 값을 지우는 우회 방지).
  - 한 접속은 줄에 하나만(답을 기다리는 동안 더 보낸 것은 버림). 떠났거나 이미 방에 있는 접속의 차례는 확인 없이 건너뜀.
  - 정직한 클라이언트는 답을 받을 때까지 잠겨 있어 잘못 거절되는 일이 없고, 같은 주소의 다른 사람은 기다릴 뿐이다.

## Steps

- [x] 3. 문서: README, FIDELITY §14
- [x] 4. 검증: vitest, tsc, 빌드, 실제 서버를 TLS로 띄워 Chromium에서 `wss://` 비밀방 입장과 틀린 암호 간격 확인

## Verification

- 단위 시험과 실제 소켓 시험(자체 서명 인증서를 시험 중에 openssl로 만들어 씀).
- Chromium: TLS 서버(자체 서명 인증서를 브라우저 컨텍스트에서 허용)에 `wss://`로 붙어 비밀방 만들기·입장, 두 컨텍스트에서 번갈아 틀려도 간격이 주소에 걸리는지.

## Results

- 단위·소켓 시험: vitest 704개 통과(주소 키·프록시 판정 8, 로비의 주소별 간격 5(예전 0.5초 시험 둘을 바꿈), 서버 5: `tlsFiles`, `startupWarning`, 주소 배선, TLS 둘). 주소 배선 시험은 서버가 주소를 로비에 넘기지 않게 바꾸면 실패함을 확인. tsc, `vite build` 통과.
- 실제 서버(TLS, 자체 서명 인증서) + Chromium 세 컨텍스트, 페이지는 vite 개발 서버, 서버 주소는 숨긴 칸에 `wss://127.0.0.1:8790/ws`: 셋 다 `wss://`로 붙어 welcome을 받음. 캔버스 방 줄 → 암호 창으로 B가 틀린 암호를 보내자 20 ms 만에 암호 창이 다시 열림. 같은 주소(127.0.0.1)의 C가 그 19 ms 뒤 맞는 암호를 보내자 495 ms 기다린 뒤 입장. 받은 메시지와 서버 로그 어디에도 암호가 없음. `https://…/health`는 ok, 같은 포트의 평문 요청은 연결이 끊김.
- vite 프록시: 8787에 헤더만 찍는 탐침을 두고 브라우저가 같은 출처 `/ws`로 붙자 `X-Forwarded-For: 127.0.0.1`(소켓 127.0.0.1)이 옴. 실제 서버(평문, 8787)를 vite 뒤에 두고 같은 흐름을 되풀이하자 C가 518 ms 기다린 뒤 입장.
- 시작 확인: `HOST=0.0.0.0`(TLS 없음)이면 평문 경고 한 줄, `TLS_CERT`만 주면 "TLS_CERT is set without TLS_KEY"로 시작하지 않음.
- 꾸민 것: 인증서는 자체 서명(컨텍스트에서 인증서 오류 무시), 모든 브라우저가 한 기계라 주소가 같음(다른 주소로 나뉘는 것은 소켓 시험의 `X-Forwarded-For`로 확인). 다른 기계에서 붙는 LAN·인터넷 경로는 돌려 보지 않음.

## Residual risks (작성 시점)

- 여러 주소에서 나눠 하는 추측은 막지 못함(주소마다 시간당 약 120번).
- 같은 NAT·프록시 주소 뒤의 사람은 서로의 틀림 간격을 함께 겪음(최대 30초 대기).
- TLS는 운영자가 켜야 함(기본은 평문).
- 루프백 소켓은 늘 믿으므로 같은 기계의 프로그램은 `X-Forwarded-For`로 제 키를 고를 수 있음. `TRUST_PROXY`에 헤더를 덧붙이지 않고 그대로 넘기는 프록시를 넣어도 같음(README에 적음).
- IPv6 /48을 가진 사람은 /64 65536개로 나눠 추측할 수 있음. 주소당 접속 수는 제한하지 않음.
- 소켓 시험의 "400 ms 이상 기다림"은 로컬 전달 지연이 100 ms 안이라는 가정에 기댐(느린 CI에서 흔들릴 수 있음).
- 화면 낭독기는 한글 입력을 위한 text 칸의 암호를 읽을 수 있음(이전과 같음).
