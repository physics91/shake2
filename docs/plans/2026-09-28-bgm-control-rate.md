# 쉐이크2 복원: 배경음 무손실 파일과 합성기 제어 주기

## Goal

배경음이 원본과 다르게 들리는 두 R 항목(FIDELITY §2.1 "부호화", "제어 주기")을 원본에 맞춘다.
- 곡 파일: Ogg Vorbis 대신, 원본 합성기의 출력 형식(22050 Hz, 16비트 스테레오) 그대로의 무손실 파일을 쓴다.
- 합성기 제어 주기: 음량과 피치를 제어 점에서만 계산하고, 그 사이를 계단 모양 직선으로 옮기는 동작을 렌더러(`tools/shakefmt/synth.py`)에 옮긴다.

## Scope

근거:

| 항목 | 내용 |
|---|---|
| 구간 나눔 | `CVoice::Mix`: 구간 끝 = min(엔벨로프·LFO가 준 다음 점, `m_stMaxSpan` = (rate+19)/20 = 1103샘플, 정지 시각, 렌더 버퍼 끝). 음량·피치는 구간 **끝** 시각의 값으로 계산 |
| 다음 점 | 엔벨로프 `GetLevel`: 공격 끝, 디케이·릴리스의 1/4·1/2·끝(100샘플 여유), 서스테인 44100. LFO: `2097152 / m_pfFrequency`(모든 LFO 깊이가 0이면 44100) |
| 계단 | `CDigitalAudio::Mix`: `dwPeriod` = (길이<<3)/max(ΔL, ΔR, 2Δ피치)/2 → 1–512로 자른 뒤 +3 & ~3. 증분은 `MulDiv(Δ, period<<8, 길이)`. `Mix16`은 `dwPeriod`샘플마다 한 계단 |
| 표 | `VRELToVFRACT`, `PRELToPFRACT`, 공격 로그 표 `snAttackTable`(200칸), LFO 사인 표(256칸) |
| 실측이 우선 | 공개 샘플(ddksynth)은 길잡이이고 기준은 이 PC의 캡처다. 출력 2배, 최소 공격 1 ms(4샘플 계단 22샘플)는 앞서 잰 값을 유지한다 |

알 수 없는 것: 합성기 싱크가 한 번에 렌더하는 길이(버퍼 끝도 구간을 자른다). 코드로는 알 수 없어 캡처에서 추정한다.
- 1차: 피치 LFO 없이 감쇠만 있는 캡처를, 같은 음을 이득 1로 렌더한 것으로 나눈다. 그러면 이득 곡선이 나오고, 그 꺾임 점 간격을 읽는다. `piano.raw`와 `piano_r2.raw`를 비교해 꺾임의 위상이 실행마다 바뀌는지도 본다.
- 막히면: 버퍼 길이 {없음, 5, 10, 20 ms}로 모델을 돌려 한 음 캡처 5개와 비교하고, 가장 가까운 값을 I로 쓴다.
- 곡 시작에 대한 위상은 실행마다 다르므로 0에 고정하고 R로 적는다. 정확도의 천장은 같은 캡처를 두 번 받았을 때의 차이(`piano` ↔ `piano_r2`)다.

범위 밖:
- 첫 재생의 첫 음 지연(실행마다 다름): 그대로 R. 리버브 입력 포화는 처음엔 범위 밖(영향 없음)이었으나, 7단계의 믹스 포화로 모델에 들어감.
- 새 의존성 없음. FLAC은 이미 쓰는 `ffmpeg`의 내장 인코더로 만든다. 호스트 Windows 실행은 계획에 없다(필요해지면 밝힌다).

저작권: 렌더한 곡과 캡처는 지금처럼 로컬 전용이다(`assets/extracted/bgm`, 스크래치). 재배포하지 않는다.

## Results

- **FLAC(1단계)**:
  - `bgm.py`는 16비트 값(`pcm16`)을 `ffmpeg` 내장 FLAC(압축 8)으로 담는다. 테스트는 파일이 렌더의 16비트 값과 비트 단위로 같은지, 22050 Hz·16비트·2채널인지 확인한다.
  - 16곡 합계 약 163 MB(예전 Ogg 28 MB). 예전 `.ogg` 16개는 지우지 않고 스크래치(`old_ogg/`)로 옮겼다. `sync-assets`는 목록에 있는 `.flac`만 `public`에 둔다.
  - Chromium 로그인 화면: `tbwait11.flac`이 65.59초로 디코드되고, 둘째 회차가 정확히 61.935초 뒤에 예약된다. 디코드된 최대값 1.022는 Chromium이 44100 Hz로 바꾸며 생긴 넘침이다. 테스트 프로필의 음악 설정은 잠시 켰다가 `off`로 되돌렸다.
  - `pytest` 106개, `music.test.ts` 4개 통과.
- **버퍼 길이(2단계)**: 이득 곡선의 꺾임 대신, 공개 샘플을 정수 그대로 옮긴 시제품(스크래치 `ctl/cr.py`)을 캡처와 샘플 단위로 맞춰 봄.
  - 제어 점이 안 바뀌는 구간은 캡처와 비트 단위로 같음. 현악 0.8–1.49초, 아코디언 유지 구간 대부분, 스네어 첫 2000샘플의 99.6%. 표·보간·곱셈·2배 출력이 맞다는 뜻.
  - 비트 일치 비율로 버퍼 길이를 고르면 441샘플(20 ms)이 피아노 두 번·현악·아코디언에서 가장 높음(최대 96%). 위상은 실행마다 다름(피아노 299, 두 번째 312, 현악 78). 곡 시작 기준 0으로 고정(R).
  - 계단은 구간 시작 뒤 `period − 2`, `2·period − 2`, …에서 오름. 공개 샘플의 C 코드(`period − 1`)보다 한 샘플 이름. 두 샘플씩 처리하는 MMX 경로로 보임. 길이 8 이하 구간은 C 경로.
  - 1초 창 오차(리버브 끔, 캡처 기준):

    | 캡처 | 이전 | 새 모델 | 실행 간 차이 |
    |---|---|---|---|
    | 피아노 유지 0.5–1.49초 | −22.0 dB | −41.8 dB | −40.5 dB |
    | 현악 유지 | −16.3 dB | −49.0 dB | −48.3 dB |
    | 첼레스타 0.5–2.5초 | −21.3 dB | −40.2 dB | |
    | 스네어 첫 6 ms | −33.9 dB | −81.8 dB | |
    | 아코디언 0.5–2.5초 | −23.6 dB | −19.8 dB | |

  - 아코디언·신스베이스의 퇴보는 노트 오프 뒤 짧은 릴리스뿐. 캡처는 노트 오프 시각보다 앞선 버퍼 시작에서 내려가기 시작하고, 새 모델은 위상 0에서 노트 오프가 버퍼 경계와 겹쳐 그 뒤 버퍼에서 내려감. 위상만 바꿔도 릴리스 창이 −28 ~ −40 dB로 좋아지므로 실행마다 다른 버퍼 위치 문제(R)로 봄.
  - 곡 단위(기존 방법 그대로):

    | 곡 | 중앙값 | 90% | 평균 |
    |---|---|---|---|
    | `tbwait22` 리버브 끔 | 0.24 → 0.20 dB | 1.92 → 1.84 dB | +0.30 → +0.21 dB |
    | mission to mizar 리버브 켬 | 0.33 → 0.30 dB | 1.25 → 1.17 dB | +0.08 → +0.01 dB |

  - 한 음 MIDI는 모든 이벤트가 441의 배수에 놓임(0.5초 = 25×441, 1.5초 = 75×441). 그래서 위상 0은 이 캡처들에 최악의 경우이고 실제 곡을 대표하지 않음.
  - LFO 확인: 신스 베이스·Celesta의 낮은 비트 일치 비율은 LFO 때문이 아님. 0.1초 블록마다 가장 잘 맞는 위상이 반 버퍼쯤 건너뛰고(297 → 75 → 297, 306 → 84 → 303), 건너뛴 위상에서는 LFO가 걸린 구간도 76–84% 비트 일치. 버퍼 위치가 한 실행 안에서도 불규칙하다는 뜻.

  - 측정 도구: `segment32.cs`에 `--dls=경로`(그 DLS를 기본 GM 컬렉션으로 등록)를 더해 호스트 `csc.exe`로 다시 빌드. 톱니 파형 DLS를 넣으면 출력값에서 위치·게인을 읽을 수 있음.
  - 32·64비트 경로가 다름: 게임이 쓰는 32비트 `dmsynth.dll`은 `period − 2` 계단과 16비트 게인, 64비트는 공개 C 루프(`period − 1`, 12비트 게인). 2단계의 `period − 2`가 32비트 경로의 실측 동작으로 확인됨(V). 앞선 한 음 훑기(64비트 포트)는 C 경로였음.
  - 믹스 포화: 음마다 16비트 포화 덧셈, 큐 순서(우선순위 낮은 것부터, 같으면 먼저 울린 것부터). 톱니 5음 두 순서의 캡처 8개가 모두 99.98% 일치. `dmvoice.mix`·`_mix`에 넣고 테스트 1개(두 경우) 추가. 리버브 입력 포화(약 2배 풀스케일)도 같은 지점이라 이제 모델에 들어 있음.
  - LFO 음량: 32·64비트 모두 버퍼 위상만 맞추면 비트 단위로 같음. 코드 변경 없음.
  - LFO 피치·벤드: 64비트(C 경로)는 버퍼 13개 비트 단위로 같음. 32비트는 20 ms 창 피치 차이 LFO 최대 1.3센트, 벤드 중앙값 0.1센트(벤드가 바뀌는 창 하나 5.2센트. 위치를 읽을 수 있는 창 4–11개만 셈). 구간 안 계단이 1–2샘플 어긋나는 곳이 있어, 위상 하나로 1.36초를 맞대면 위치 차이가 LFO 0.5–0.9샘플, 벤드 약 4샘플까지 쌓임. "구간 마지막 증분에 목표 피치" 규칙은 반대 사례가 있어 넣지 않음.
  - 곡 시간: DirectMusic은 틱을 768 PPQ로 내림 변환(21틱 간격 캡처의 134·135 순서. 간격 절대값은 예측보다 약 0.3% 짧고 원인 미확인). `midi.py`에 넣고 테스트 1개 추가. 5틱 배수가 아닌 이벤트가 15곡에 곡당 3–2,417개 있어 이 곡들의 음 시각이 1음악 틱 미만(120 BPM에서 0.65 ms 미만) 당겨짐. `tbwait22`에는 해당 이벤트가 없음.
  - 검증: `pytest` 119개 통과. 게이트: 한 음 창은 전과 같은 수준(피아노 −41.8 dB, 현악 −49.1 dB, 첼레스타 −40.3 dB, 드럼 −inf), 곡 단위 `tbwait22` 0.20·1.85·+0.21 dB, mizar 0.30·1.15·+0.01 dB.
  - 다시 렌더(1분 31초, 믹스 포화·16비트 게인·768 PPQ 모두 반영): 잘린 샘플 합계 57,833 → 57,772(mizar 19,541, 캡처 19,676). `loop_end`는 16곡 모두 같음. 곡 길이는 13 ms 늘었는데, 16비트 게인이 꺼져 가는 꼬리의 아주 작은 값을 292샘플 더 남기기 때문(±8 이상 샘플이 끝나는 곳은 같음).
  - `sync-assets` 16곡. Chromium: 16곡 모두 22050 Hz로 디코드되고 길이가 `index.json`과 같음, `tbwait22` 실시간 재생 1.5초 확인. `shake2.music`은 처음부터 없었고 건드리지 않음.

## Residual risks

- 버퍼 위치(R): 실행마다, 한 실행 안에서도 달라 재현하지 않음. 음마다 제어 점이 최대 한 버퍼(20 ms)까지 원본의 어느 한 실행과 다를 수 있음. 원본끼리도 그만큼 다름.
- 441샘플은 맞춘 값(I). `period − 2` 계단과 16비트 게인은 32비트 캡처로 확인했지만(V), dmsynth.dll 코드는 보지 않았음(블랙박스 측정만).
- 32비트 경로의 피치 계단 시점은 구간 안에서 1–2샘플 어긋나는 곳이 있어 비트 단위로 맞추지 못함(I–R). 피치 차이는 20 ms 창에서 1.3센트 이하로 들리지 않는 수준이지만, 파형 위상은 원본과 다를 수 있음.
